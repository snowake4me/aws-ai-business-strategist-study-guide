## Q9 — Platform migration readiness: pilot vs representative-load test (D2, skill 2.1.5) ✗ [flagged] · review D2 #13 · timer 0:00 (artifact)

**Scenario:** A business process already running in production on one GenAI platform
is being moved to Bedrock. The stem states the daily volume, names a weekly peak, and
says data and access controls are unchanged. Select TWO pre-cutover actions.

- **What I picked:** Pricing Calculator estimate including the parallel-run period ✓,
  plus a short pilot on a small set of typical documents ✗
- **What was correct:** Pricing Calculator estimate ✓, plus test at representative
  volumes and compare response times against the current platform's baseline

**Discriminator:** The stem plants two facts the right answer must use: a **volume
profile with a peak**, and an **existing production system to baseline against**. The
pilot option discards both. "Small set" is not representative of 8,000 a day, and
"typical" documents explicitly exclude the Monday spike the stem went out of its way to
mention.

**Why missed:** Reached for the safe-sounding word. "Pilot" reads as prudent and
incremental, which is the register the exam rewards elsewhere, so it passed the sniff
test without being checked against the numbers in the stem. Scope-shrink distractor:
an option that does a *smaller* version of the right thing, dressed as caution.

**Mental model:** Pilot and load test answer different questions.

| Question the business is asking | Instrument | When |
|---|---|---|
| "Does this new capability create value at all?" | **Pilot / POC** on a small representative slice | New use case, Experiment level, nothing in production yet |
| "Will a process that already works survive a platform move?" | **Representative-volume test against the current baseline** | Migration between platforms, process already in production |

Skill 2.1.5 is the second row: "transition business processes ... between AI
platforms" with business continuity and performance impact as the named
considerations. When the stem is a migration, a pilot is the wrong instrument no
matter how sensible it sounds. Skill 2.2.2 (establish baseline metrics before
implementing) is the same rule from the measurement side: the baseline is only
useful if you test at a load comparable to what it was measured under.

**Trigger phrases:** "already in production" · "move the workload to" · a stated
volume · a stated peak ("higher on Monday mornings", "month-end", "holiday season").
Any of these means an option that says *small*, *typical*, *sample*, or *subset* is
failing the constraint the stem planted.

**Reinforcement:** Flashcard (one-keyword decision: migration → baseline load test,
not pilot). Candidate for `decision-patterns/exam-traps.md` as the first entry: **the
stem plants a number; one option honors it, one option shrinks it.**

**Rationale check:** TD's explanation is consistent with the exam guide's 2.1.5
language and with AWS Well-Architected performance-testing guidance. No conflict with
a primary source.

## Q10 — KPI set for a predictive-maintenance pilot: outcome vs model vs activity metrics (D2, skill 2.2.1) ✗ [flagged] · review D2 #7 · timer 0:00 (artifact)

**Scenario:** A predictive-maintenance pilot is working and leadership wants KPIs to
decide on expansion. The stem asks for KPIs that capture **both** measurable financial
impact **and** workforce efficiency. Single answer, four three-metric bundles.

- **What I picked:** avoided downtime cost + prediction precision by equipment type +
  percentage of maintenance alerts reviewed by technicians
- **What was correct:** avoided downtime cost + maintenance labor hours per completed
  repair + work orders completed per technician shift

**Discriminator:** Two requirements in the stem. Every option leads with a plausible
financial metric, so the first element decides nothing. The second and third elements
must be **workforce efficiency**, meaning labor per unit of output or output per unit of
labor. Hours per repair and work orders per shift are exactly that. Precision is a
model-quality metric. "Alerts reviewed" is an adoption/activity metric: it says
technicians are *looking*, not that they are getting more done.

**Why missed:** Anchored on the shared correct first element, then accepted two
adjacent-sounding metrics for the second requirement without testing them against the
word *efficiency*. "Percentage of alerts reviewed by technicians" has a human in it and
so passed as a people metric. Same shape as Q9: a two-requirement stem, an option that
satisfies one requirement and substitutes something that merely sounds like the other.

**Mental model:** Four KPI classes. Only the first two are business-value KPIs.

| Class | Examples | Answers "business value"? |
|---|---|---|
| **Financial outcome** (tangible) | avoided downtime cost, cost reduction, revenue lift | Yes |
| **Workforce / process efficiency** (intangible-to-tangible) | labor hours per unit, units per shift, cycle time, time saved | Yes |
| **Adoption / activity** | % alerts reviewed, recommendations generated, % equipment connected, active users | No. Leading indicator at best (skill 2.2.4). |
| **Technical / model quality** | precision, inference latency, system availability | No. Engineering health, not value. |

Rule: in a "business value" KPI question, any metric that describes **the model**,
**the system**, or **how much people used it** is a distractor. Keep only metrics that
describe **what the business got**. If the stem names two value dimensions, each
non-financial element must independently pass the efficiency test.

**Trigger phrases:** "justify expansion" · "business value" · "financial impact and
[X]" · "return on investment". Distractor tells: *precision*, *accuracy*, *inference
time*, *availability*, *percentage connected*, *percentage reviewed*, *number
generated*.

**Reinforcement:** Flashcard (KPI class table). Second D2 miss with the same
two-requirement shape as Q9; if a third appears, this becomes the first theme.

**Rationale check:** TD's split between business-outcome KPIs and technical or
adoption metrics matches the exam guide's 2.2.1 language (tangible plus intangible
benefits) and the Cloud Value Framework's staff-productivity pillar. No conflict.

## Q13 — Is AI appropriate? Rules stated in the stem vs "lots of data" bait (D2, skill 2.1.4; also 1.2.1) ✗ [flagged] · review D2 #14 · timer 0:00 (artifact)

**Scenario:** A delivery company wants to put AI into a billing step that adjusts fees
for late shipments. The stem **spells out the policy**: a fixed percentage above one
lateness threshold for priority, a different fixed percentage above another threshold
for standard, and a named exception (severe weather) that gets nothing. It then adds
that volume is high and years of records exist. Single answer: is AI appropriate?

- **What I picked:** Yes, AI can learn the appropriate adjustment from historical
  delivery records
- **What was correct:** No, the adjustment is fully determined by the stated
  service-level, delay-time, and exception rules

**Discriminator:** The stem already contains the complete decision function. Three
if-then rules with explicit thresholds and one explicit exception. Nothing is left to
learn. "Thousands of shipments a day" and "several years of records" are **enablers**
of ML, not **needs** for it, and the stem planted them as bait. The question to ask is
not "could ML do this" but "is there anything here that a rule cannot already do."

**Why missed:** Read *high volume + historical data* as the AI signal and stopped
reading. The three rules in the first sentence were the answer, sitting in plain sight,
and the volume sentence at the end overrode them. Third D2 miss in a row where an
option that sounds strategic and AI-forward beat the option that used the facts the
stem planted.

**Mental model:** AI vs rules, decided by one question.

| Can the output be fully written as rules from what the stem gives you? | Answer |
|---|---|
| Yes: thresholds, fixed percentages, named exceptions, lookup tables, policy text | **Rules.** AI adds cost, monitoring, drift, and explainability burden for zero gain. |
| No: the mapping must be inferred (pattern recognition, prediction, unstructured input, judgment that varies case by case) | **AI.** |

Things that do **not** move a problem from the top row to the bottom row: data volume,
years of history, transaction rate, "at scale," structured or numeric data. Things that
do: the stem says the outcome *depends on patterns*, *cannot be defined in advance*,
*varies in ways the policy does not capture*, or involves free text, images, or
forecasting.

The exam guide lists this twice (1.2.1 and 2.1.4), and the Responsible AI Lens
itself says its guidance "is not appropriate for AI use cases that can be solved
without machine learning, for example, by using expert systems." Expect "No, use
rules" to be correct more than once on the real exam. It is the AWS-canonical position,
not a trick.

**Trigger phrases for the rules answer:** the stem *states the policy* ("receive a
15% adjustment", "more than 6 hours late", "no adjustment for X") · "consistently" ·
"established rules" · "predefined". **Bait phrases:** "processes thousands per day" ·
"years of historical records that could be used" · "as volume grows". When the bait
phrases appear *after* a stated policy, they are there to be ignored.

**Reinforcement:** Flashcard (the one-question test). Also the second entry for
`decision-patterns/exam-traps.md`: **volume and history are enablers, not needs.**

**Rationale check:** Consistent with AWS's own "when to use ML" guidance (ML is
unnecessary when the target can be determined by rules or computation) and the RAI
Lens expert-systems caveat. No conflict.

## Q18 — Training vs inference: what happens "each morning" (D1, skill 1.1.1) ✗ [flagged] · review D1 #6 · timer 0:00 (artifact)

**Scenario:** A demand-forecasting model built on SageMaker AI from a year of sales
history. Each morning it receives recent sales figures and returns a quantity to
prepare. The stem states separately that the model is **retrained on a fixed schedule
every couple of months**. Single answer: what does the system do each morning?

- **What I picked:** it uses the recent sales data to update the model parameters as
  part of producing the daily prediction
- **What was correct:** it uses a trained model to perform inference and generate a
  prediction

**Discriminator:** Two facts in the stem, one per lifecycle stage. "Updates the model
every two months" is the only place parameters change. "Each morning receives data and
returns an estimate" is inference. The picked option says *update the model
parameters* daily, which directly contradicts the stated retraining schedule. The
schedule sentence was there to eliminate exactly that option.

**Why missed:** Surface-word match. The stem said "recent sales information" and the
option said "recent sales data," so it read as the option that used the stem. But the
verb was wrong. *Update the parameters* is training vocabulary; inference never
modifies the model. A daily input to a deployed model is just an input.

**Mental model:** Parameters change in exactly one place.

| Stage | Input | What changes | Output |
|---|---|---|---|
| **Training / retraining** | historical labeled data, on a schedule or trigger | the model's parameters (weights) | a new model artifact |
| **Inference** | new, unseen input | **nothing in the model** | a prediction |

Anything that says the model *learns*, *updates its parameters*, *retrains*, or
*incorporates* new data is describing training. If the stem gives a separate
retraining cadence, every daily or per-request option that touches the model is wrong
by construction.

**Trigger phrases:** "each morning / each request / in real time" plus "returns a
prediction" = inference. "Updates the model every N months" = the *only* training
event in the scenario. Distractor tells: *update parameters*, *retrain before
generating*, *uses each prediction as training data*.

**Reinforcement:** Flashcard (one-keyword: parameters change only in training). First
D1 miss; a vocabulary-precision miss rather than a strategy miss, but the same
underlying error as the D2 set: the stem stated the fact that killed the picked option.

**Rationale check:** Consistent with the SageMaker ML-concepts doc TD cites. One
sloppiness note: TD's own infographic says "every three months" while the stem says
two. Harmless here, but it is the kind of internal inconsistency to expect from a bank
written before anyone sat the exam. Verify numbers in rationales, not just logic.

## Q51 — Two GenAI symptoms, two limits: context window vs max output tokens (D1, skill 1.3.2) ✗ [flagged] · review D1 #5 · 1:26

**Scenario:** A GenAI app that writes evaluation reports works fine on small sourcing
projects. On large ones, where several proposals, notes, and policy documents share a
session, two things go wrong: relevant details go missing, and some reports stop
before all sections are written. No retraining allowed. Select TWO changes.

- **What I picked:** raise the maximum response length ✓, plus preserve the full
  conversation history and include every supporting document in each request ✗
- **What was correct:** raise the maximum response length ✓, plus limit each request
  to the proposal sections, notes, and policies most relevant to that assessment

**Discriminator:** Two symptoms, and each maps to a different limit.

| Symptom in the stem | Cause | Fix |
|---|---|---|
| Works on small projects, loses details on large ones | **Input exceeds the context window.** The model is already dropping or under-weighting content. | Send less, chosen by relevance. |
| Report ends before all sections are done | **Max output tokens too low.** | Raise the response length. |

The tell for symptom one is *works small, fails large*. Failure that scales with input
size is a context-window problem, full stop. Adding *more* input to fix a problem
caused by too much input is the one option that makes it worse.

**Why missed:** Reasoned to the wrong answer rather than skimmed to it. The worry was
that limiting the request would exclude relevant details. But the stem says details
are *already* being excluded, with everything included, by the model, uncontrollably.
The correct option does not say "cut content." It says "most relevant to the specific
assessment," which moves the selection from the model's silent truncation to a
deliberate relevance choice. That is what RAG-style retrieval does at the mechanism
level, and skill 1.3.3 sits right next to 1.3.2 in the guide for that reason.

This is the one D1 miss that is a **misconception**, not a reading error: "more
context means fewer missing details." It is backwards once the window is full. If it
was unflagged, it is a true blind miss and the most important item on this list.

**Mental model:** Symptom-to-lever table for GenAI without retraining.

| Symptom | Lever |
|---|---|
| Details missing, and it correlates with input size | Curate or chunk the input (context window) |
| Output truncated mid-structure | Raise max output tokens |
| Output inconsistent or random across identical requests | Lower temperature / top-p |
| Output bland, repetitive, or identical when variety is wanted | Raise temperature / top-p |
| Model lacks facts it was never trained on | RAG (retrieval) |
| Model has the facts but the wrong style, format, or domain tone | Fine-tuning |

Temperature and top-p never change *how much* fits in or comes out. They only change
*which* tokens are chosen. Any option that offers a sampling parameter for a capacity
symptom is a distractor.

**Trigger phrases:** "performs consistently for smaller" + "for larger ... missing" =
context window. "ends before all required sections" = output limit. "without
retraining" = the answer lives in prompt construction and inference parameters, not
model adaptation.

**Reinforcement:** Flashcard for the symptom table, and this is the first candidate for
a `decision-patterns/genai-levers.md` cheat card, since the exam guide's 1.3.x skills
are all variations of "which lever for which symptom."

**Rationale check:** Consistent with Bedrock inference-parameter docs (max tokens,
temperature, top-p) and with AWS prompt-engineering guidance on context management.
No conflict. The objection about excluding details is a fair instinct in general but
is answered inside the stem itself.

## Q65 — Rules workflow vs AI agent: when the next step depends on the last result (D1, skill 1.2.2) ✗ [flagged] · review D1 #2 · 1:41

**Scenario:** A retailer's AI assistant already answers policy questions and
summarizes order information. They now want it to **review each request and choose
the next step**, which may be checking status, issuing a replacement, issuing a
refund, or escalating, **depending on the case and on the result of a previous
action**. Single answer, BEST solution.

- **What I picked:** a rules-based workflow across the customer service systems
- **What was correct:** an AI agent integrated with order management, replacement,
  refund, and escalation tools

**Discriminator:** "Choose the appropriate next step ... depending on the case ...
based on the result of a previous action." Three phrases that all say the same thing:
the path is not enumerable in advance and each step's outcome decides the next. That
is the definition of an agent in the exam guide's own words for 1.2.2: autonomy, tool
use, orchestration. The four named actions (status, replacement, refund, escalation)
are **tools** that act on external systems, which a chatbot or a RAG assistant cannot
do. The stem even tells you the RAG assistant is what they *already have*.

**Why missed:** The mirror image of Q13. There, the stem spelled out the rules and the
pick was AI. Here, the stem said the path depends on runtime results and the pick was
rules. Same axis, wrong side both times, which means the boundary itself is not held
precisely rather than one tendency being over-applied. Possibly also "rules-based"
reading as the safe, governable choice, the same register bias as the D2 set.

**Mental model:** The AI capability ladder. The stem tells you which rung by what the
system must *do*.

| What the system must do | Rung |
|---|---|
| Follow a decision path that can be fully written in advance | **Rules / workflow** (Step Functions-style state machine) |
| Answer questions from general knowledge | Chatbot |
| Answer questions grounded in company data | **RAG assistant** (Knowledge Bases) |
| **Take actions in external systems, choosing the next action from the result of the last** | **Agent with tools** |

Rules vs agent, decided by one question: **can every path be enumerated before the
first request arrives?** Yes means workflow. No, because branch N depends on what
branch N-1 returned, means agent.

Pairing with Q13 gives the full rule. Stem *states the rules* (thresholds, fixed
outcomes, named exceptions) → rules. Stem says *choose*, *depending on the case*,
*based on the result of a previous action*, *may need to* → agent. Stem says *answer*,
*summarize*, *explain*, grounded in documents → RAG assistant, not agent.

**Trigger phrases for agent:** "choose the next step" · "depending on the result" ·
"based on a previous action" · a list of *actions* on external systems (process,
issue, create, escalate). **Trigger phrases against agent:** the current solution
"answers questions" and nothing in the new requirement changes external state.

**Reinforcement:** Flashcard (the ladder). Combined with Q13 this is the second theme,
and the ladder belongs in a `decision-patterns/` cheat card.

**Rationale check:** Consistent with the exam guide's 1.2.2 capability list (autonomy,
tool use, agent-to-agent, orchestration) and with the Agentic AI Security Scoping
Matrix's framing of agents as systems that act. No conflict.
